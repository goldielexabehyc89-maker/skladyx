## Этап 5. Новая логика сотрудников

Цель: адаптировать складскую логику под новую организацию.

- [x] Пакет 1 — мультироли РостАгро:
  RECEIVER, LOADER, PICKER, CONTROLLER, OBSERVER.
  Рабочие смены WorkShift: одна активная роль и один склад на смену,
  read-only доступ к остаткам и истории.
  Выполнено 2026-07-30, коммит `8b15b22`,
  миграция `20260730180000_work_shifts_and_roles_s5p1`.
  Проверено локально, на staging и prod.
  Legacy-роли и старые процессы STOREKEEPER сохранены, S6 отложен.

- [x] Пакет 2 — WorkflowTask, очередь задач, приоритеты и автоматическое назначение.
  Транзакционный движок очереди (server-only): создание по dedupeKey, авто-назначение по
  загрузке смены, приоритет URGENT со skip-по-причине, зависимости BLOCKED→QUEUED с
  tenant-изоляцией, передача задач с двойным подтверждением и защитой от устаревания.
  Возврат невзятых задач в очередь и блокировка завершения смены при незавершённой
  физической операции. ADMIN с рабочей сменой видит свою очередь (переключатель
  «Мои задачи/Монитор»). За флагом `WORKFLOW_TASKS_ENABLED`.
  Выполнено 2026-07-30, коммит `d4f6064`, миграция `20260730190000_workflow_tasks_s5p2`.
  Проверено локально, на staging и prod.

- [x] Пакет 3 — зоны склада, уровни ячеек и правила размещения.
  Гибрид зон: системный `ZoneKind` (RECEIVING/STORAGE/COOLING/CONTROL/ISSUE/DISCREPANCY/
  BUFFER) + настраиваемые `WarehouseZone`. Виртуальные зоны — «одна большая ячейка»;
  физические содержат `Cell` с `zoneId`/`level` (STORAGE — уровень ≥ 1); `isStaging`
  синхронизирован с зоной ISSUE; занятую ячейку в другую зону перенести нельзя. Ядро
  остатков не тронуто. Чистый policy-хелпер размещения по уровням. За флагом
  `WAREHOUSE_ZONES_ENABLED`. Выполнено 2026-07-31, коммит `9b3563c`, миграция
  `20260730194359_warehouse_zones_s5p3`. Проверено локально (Node 22, Docker), на staging и prod.

- [x] Пакет 4 — приёмка группами и температурный контроль.
  Неделимые группы приёмки (HandlingGroup), маршрутизация по температуре
  (≤X → хранение, >X → охлаждение), размещение группы одним движением, инвариант
  «одна ячейка = одна группа». Техническая реализация завершена. За флагом
  `GROUP_RECEIVING_ENABLED`. Доставлено на prod, миграция
  `20260731110000_group_receiving_s5p4` (коммиты `020b075`/`b54aa11`/`a53f8dd`).
  Код и миграции проверены на prod при выключенном флаге; полноценные бизнес-сценарии
  проверены на staging. На prod бизнес-процесс НЕ активирован: `GROUP_RECEIVING_ENABLED=false`.

- [x] Пакет 5 — охлаждение и автоматические срочные задачи.
  Сессия охлаждения (снимок X/R), резерв STORAGE-ячейки ур.3+, отложенная срочная задача
  «Забрать из охлаждения» (`WorkflowTask.availableAt`), повторный замер и атомарный вывоз
  всей группы при temp ≤ X с приоритетом свободных нижних уровней (1 → 2), иначе — верхний
  резерв ур.3+; отмена активного охлаждения запрещена. Техническая реализация завершена.
  За флагом `COOLING_WORKFLOW_ENABLED`. Выполнено 2026-08-04, коммит `287fde3`, миграция
  `20260731120000_cooling_s5p5`. Код и миграции проверены на prod при выключенном флаге;
  полноценные бизнес-сценарии (e2e трёх вариантов размещения) проверены на staging.
  На prod бизнес-процесс НЕ активирован: `COOLING_WORKFLOW_ENABLED=false`.

- [ ] Активация Пакетов 4–8 на prod: создать реальные справочники РостАгро, определить
  порог X и `Warehouse.coolingRate` R, подключить интеграционный адаптер импорта внешних
  заказов, записать настройки защищённой серверной командой и только затем включить флаги.
  Первые операции должны быть реальными, без тестовых складских движений.

- [x] Пакет 6 — сборка внешних заказов.
  Импорт внешнего заказа (ADMIN/интеграционный адаптер) → FIFO-резерв на точную
  строку-источник (`StockReservation`, Σ активных ≤ баланс) → перестановка группы
  погрузчиком с нижних уровней (MOVE_GROUP; бронь ячейки `CellReservation.taskId`;
  подъём лишней группы наверх / спуск нужной вниз; из группы, едущей наверх, не
  резервируем) → сборка сборщиком по QR ячейки+группы с серверной сверкой → зона
  CONTROL → `IN_CONTROL`. Идемпотентный повтор финального скана; очередь
  `priority→dueAt→createdAt`. Техническая реализация завершена. За флагом
  `EXTERNAL_ORDER_PICKING_ENABLED`. Выполнено 2026-08-04, коммит `d56e3fb`, миграции
  `20260804150000_external_orders_s5p6` + `20260804160000_move_reservation_task_s5p6b`.
  Доставлено local → staging → prod. Код и миграции проверены на prod при выключенном
  флаге; полноценные бизнес-сценарии (e2e: сборка/перестановка/идемпотентность/отказы,
  lift-конфликт двух заказов) проверены на staging. На prod бизнес-процесс НЕ активирован:
  `EXTERNAL_ORDER_PICKING_ENABLED=false`; импорт, резерв и сборка не активированы —
  активация ждёт реальные справочники РостАгро и интеграционный адаптер импорта.

- [x] Пакет 7 — контроль заказа, исправление и полный повторный контроль.
  При IN_CONTROL (флаг ON) создаётся CONTROL_ORDER контролёру: скан QR заказа, затем скан QR
  каждой группы/товара + количество (сервер сверяет tenant/склад/связь с заказом; неожиданный
  товар — отдельной строкой). Нет расхождений → CONTROL_PASSED. Есть → CORRECTION_REQUIRED +
  срочная CORRECT_ORDER сборщику (первонач. если на смене, иначе наименее загруженному): каждое
  расхождение разрешается отдельно (завершение заблокировано до разрешения всех), недостача —
  выравнивание без движения, излишек/не тот/повреждённый — возврат/изоляция в DISCREPANCY через
  ядро (stock.ts). После разрешения — ПОЛНЫЙ повторный контроль; история попыток не редактируется.
  За флагом ORDER_CONTROL_ENABLED. Выполнено 2026-08-05, коммиты `5220847` (база) + `8ec9e30`
  (коррекция), миграции `20260804170000_order_control_s5p7` + `20260805120000_control_resolution_s5p7b`.
  Доставлено local → staging → prod. Код и миграции проверены на prod при выключенном флаге;
  полноценные бизнес-сценарии (e2e контроля/исправления по скану) проверены на staging. На prod
  бизнес-процесс НЕ активирован: `ORDER_CONTROL_ENABLED=false`.

- [x] Пакет 8 — размещение в зоне выдачи и выдача водителю.
  После `CONTROL_PASSED` при включённом флаге автоматически резервируется свободная
  ячейка зоны ISSUE и создаётся срочная задача `ISSUE_ORDER` погрузчику. Если ячейки
  нет, заказ переходит в `AWAITING_ISSUE_CELL` без создания задачи. Размещение выполняется
  по сканам QR заказа, ячейки и группы; крупный заказ может занимать несколько ячеек.
  Одна активная ячейка выдачи принадлежит только одному заказу. После полного переноса
  из CONTROL заказ переходит в `READY_FOR_DRIVER`. Выдача выполняется по QR заказа и
  всех его ячеек, без подтверждения водителя; остаток списывается через `stock.ts`,
  ячейки освобождаются, ближайший ожидающий заказ активируется автоматически.
  Реализовано с разделением количеств разных заказов одной партии и конкурентной защитой
  ячеек выдачи. За флагом `ORDER_ISSUE_ENABLED`. Выполнено 2026-08-06, коммит `8c2dc92`,
  миграция `20260805130000_order_issue_s5p8`. Доставлено local → staging → prod.
  Код и миграция проверены на prod при выключенном флаге; бизнес-сценарии, включая
  общую партию двух заказов и гонки за ячейку, проверены на staging. На prod процесс
  НЕ активирован: `ORDER_ISSUE_ENABLED=false`.

- [x] Пакет 9A — настройки склада, фиксация 7 системных зон, ручное/массовое управление
  ячейками, печать QR/Code 128, основа EAN номенклатуры, подготовка сканера.
  За флагом `WAREHOUSE_ZONES_ENABLED`. Выполнено 2026-08-06, commit `fbab411`,
  миграция `20260806120000_settings_ean_zones_s5p9a`. Доставлено local → staging → prod.
  Бизнес-процессы Пакетов 4–8 на prod не активированы. Перевод операций на заводской EAN — Пакет 9B.
