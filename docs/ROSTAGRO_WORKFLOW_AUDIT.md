## 0. Резюме

Текущая система — **документо-ориентированный** складской модуль с сильным транзакционным ядром
остатков. Целевая логика РостАгро — **задаче-ориентированный** workflow (очередь задач,
балансировка, охлаждение, уровни, FIFO-резервы, контроль, выдача внешнему водителю).

- **Что уже есть и ценно:** централизованное ядро остатков (`src/lib/stock.ts`), append-only
  ledger + материализованный баланс, мультитенантность через `companyId`/`scoped()`,
  инвентаризация через ядро, SSE-realtime, семейство `PickList*` с мультиячейкой staging.
- **Чего нет вовсе (greenfield):** смены, общая очередь задач, приоритет/срочность, назначение по
  нагрузке, зоны/уровни ячеек, охлаждение и температура, внешние заказы, **хранимые** резервы,
  контроль/исправление как процесс, выдача водителю.
- **Ключевые противоречия (детали ниже):** (1) push-уведомления шлются в 3 местах — конфликт с
  правилом «без уведомлений»; (2) резерв считается на лету без блокировки — латентная гонка;
  (3) три пути записи остатка **в обход** ядра.

**Сохранность остатков пока НЕ доказана** — доказано лишь наличие хорошего ядра. Критерий
доказанности — §7.

## 2. Текущие инварианты (что нельзя нарушать)

1. **Единая точка изменения остатков** — `src/lib/stock.ts`. `applyLotMovement(tx,…)` `:54` и
   `moveUnit(tx,…)` `:114` требуют `Prisma.TransactionClient` (нельзя вне транзакции).
2. **Защита от минуса и гонки** — атомарный условный декремент:
   `tx.stockBalance.updateMany({ where:{ lotId, locKey, qty:{ gte: qty } }, data:{ qty:{ decrement } } })`
   → `if (res.count !== 1) throw StockError` — `src/lib/stock.ts:88-92`.
3. **Модель мест** — `locKey`: `C:<cellId>` / `W:<warehouseId>` / `E:<userId>` / `EP:<userId>` —
   `src/lib/stock.ts:21-32`; `null` = внешний мир (приход/расход).
4. **Ledger append-only** — `StockMovement` только создаётся (`:71`, `:139`), не обновляется.
   Материализованный `StockBalance` upsert/decrement — `:88-109`.
5. **Мультитенантность** — `companyId` на всех доменных моделях (кроме join `UserWarehouse`
   `schema.prisma:163` и `AuthToken` `:174`); доступ через `scoped(session)` `src/lib/tenant.ts`,
   `resolveCompanyId` `:16-19`.
6. **Атомарная нумерация документов** — `Counter` (`@@id([companyId,docType])` `schema.prisma:307`)
   через `nextNumber(tx,…)` `src/lib/counters.ts:9-20`, внутри транзакции документа.
7. **Паттерн server action** — `requireX()` → `scoped()` → zod → `prisma.$transaction` →
   `logEvent` → `revalidatePath` (напр. `receiveOrderScanAction` `supplier-orders.ts:356`).
8. **Realtime после коммита** — `broadcastRealtime` вызывать после транзакции — `src/lib/realtime.ts:59-60`.

## 6. Мультитенантность и уникальность (риски изоляции)

- `companyId` есть на всех доменных моделях; отсутствует только на join `UserWarehouse`
  `schema.prisma:163` и `AuthToken` `:174` (scoped через FK) — приемлемо.

## 7. Критерий «сохранность остатков доказана»

Сохранность — **обязательная цель, пока не доказанная**. Считается доказанной, когда одновременно:

1. Полная карта всех write-path остатка задокументирована (§4 — выполнено на HEAD).
2. Для каждого обхода ядра (§4: приёмка units, удаление приёмки, off-ledger резерв) определено
   правило миграции: привести к ядру, либо явно обосновать и покрыть тестом.
3. Есть тесты конкурентности (§8), доказывающие отсутствие двойного списания/двойного резерва.

До выполнения всех трёх пунктов ни один этап, меняющий движение товара, не считается безопасным
для prod.

## 8. Тесты: существующие и недостающие

**Существующие** (`scripts/`):
- `verify-stock.ts` — ядро: назначение ячейки, **защита от минуса** `:103`, выдача EP→E,
  единицы, инвентаризация ±, сверка ledger↔баланс `:256`.
- `verify-http.mjs` — сквозной no-JS прогон (логин, склад, ячейки, товары, приёмка, роль-скоуп,
  выдача по бейджу, изоляция EMPLOYEE, legacy `/app`).
- `verify-realtime.mjs` — SSE (401 без сессии, доставка, роль-фильтр, reconnect).
- `verify-mobile.mjs` — мобайл-лейаут (нет горизонтального скролла, нет видимых таблиц).

**Недостающие (для целевой логики):**
- **Конкурентность резерва:** два параллельных резерва одного lot не превышают доступное.
- **Конкурентность задач:** одну задачу/ячейку/группу не получают двое.
- **Идемпотентность:** повтор скана не двоит движение; повтор webhook не двоит заказ.
- **Охлаждение:** пересчёт замера, снимок X/R, срочный вывоз.
- **FIFO:** выбор старейшей группы, строка из нескольких групп, частичное покрытие.
- **Цепочки перестановок:** низ→буфер→низ, откат частично выполненной цепочки.
- **Смена:** передача незавершённой физической операции, запрет завершения при взятом товаре.
- **Миграция:** backfill `isStaging`→зоны на копии данных; сверка ledger до/после.

## 9. Обязательные результаты аудита (модели/инварианты для DESIGN)

**9.1. Матрица разрешений по 7 целевым ролям** (что видит / что делает):

| Роль | Видит | Делает |
|---|---|---|
| Технический суперадмин (SaaS) | все организации/контуры | управление SaaS; **не** обычная роль склада |
| Администратор | всё в организации | настройки, сотрудники, роли, исправления, закрытие смен; складские операции — с аудитом |
| Кладовщик-приёмка | свои приёмки текущей смены | приёмка сканом: товар, кол-во, температура |
| Кладовщик-погрузчик | свою очередь перемещений | охлаждение, размещение, перестановки, контроль→выдача, выдача водителю |
| Кладовщик-сборка | свою очередь заказов | сбор с 1–2 уровней, передача в контроль |
| Контролёр | очередь контроля, расхождения, инвентаризации | проверка заказов, отправка ошибок на исправление, инвентаризация |
| Наблюдатель | отчёты, история, остатки | только чтение |

Разрыв: текущие 3 роли (`schema.prisma:18-22`) не покрывают эту матрицу; гварды бинарны
(`auth.ts:48-59`).

**9.2. Системные/виртуальные зоны** — зона приёмки, зона контроля, зона расхождений учитываются
как «одна большая ячейка» (системное место). В текущей модели `Cell` таких системных мест нет
(`schema.prisma:258-264`); `locKey` поддерживает только `C:/W:/E:/EP:` (`stock.ts:21-32`) — нужен
системный тип места (кандидат в DESIGN).

**9.3. Целевые инварианты (перенести в DESIGN и обеспечить):**
- одна принятая группа = одна паллета = одна ячейка при размещении (смешивание групп запрещено);
- один заказ может занимать несколько ячеек выдачи; одна ячейка выдачи — только один заказ;
- у погрузчика одновременно одна активная физическая задача;
- при завершении смены незавершённая физическая операция передаётся (обе стороны подтверждают)
  либо смену нельзя завершить;
- готовый после охлаждения товар не остаётся в зоне охлаждения;
- невыполнимая физическая операция не назначается как обычная задача;
- расхождения не правятся прямым редактированием остатка — только через инвентаризацию/ядро.
