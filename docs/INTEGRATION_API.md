# Нейтральный API интеграции (Этап 5 / Пакет 10)

Общий REST-контракт для загрузки номенклатуры и заказов из внешней системы. Формат конкретной 1С
здесь **не зашит** — адаптер к 1С (или любой другой системе) будет **тонким преобразователем** этого
контракта: он приводит выгрузку источника к JSON ниже и вызывает эти endpoint'ы.

Версия контракта: `v1`. Базовый путь: `/api/integration/v1`.

## Включение

Два серверных окружения (в `.env` контура, не в репозитории):

```
INTEGRATION_API_ENABLED=false      # true — API отвечает; иначе все запросы → 404
INTEGRATION_API_TOKEN=             # длинный случайный секрет (напр. openssl rand -base64 32)
INTEGRATION_API_ORG_SLUG=          # slug организации, которой принадлежит токен (напр. rostagro)
```

- Токен свой на каждый контур; не коммитить, не логировать, не возвращать клиенту.
- Пока `INTEGRATION_API_ENABLED != "true"` — endpoint'ы отвечают `404` (существование не раскрывается).
- Токен **привязан к организации**: `INTEGRATION_API_ORG_SLUG` задаёт единственный slug, которому
  разрешён доступ. Пустой slug при включённом API → доступ закрыт (fail-closed). Даже с верным
  токеном запрос на host **другой** организации отклоняется (`404`) — токен одного tenant'а не работает
  на чужом tenant-host.

## Аутентификация

Заголовок:

```
Authorization: Bearer <INTEGRATION_API_TOKEN>
```

- Сравнение токена — постоянное по времени (constant-time); значение нигде не логируется.
- Нет заголовка / неверный токен / пустой серверный токен → `401`.

## Определение организации

Организация определяется **по адресу запроса (host)**: `rostagro.skladyx.ru` → организация `rostagro`
(на staging — `staging-rostagro.skladyx.ru`). Поля `companyId`, `warehouseId`, `userId` из тела запроса
**не принимаются** — их подстановка невозможна. Неизвестный host → `404`. Организация по host должна
совпадать с `INTEGRATION_API_ORG_SLUG`, иначе — `404` (см. «Аутентификация»).

## Общие ответы и коды

| Код | Значение |
|-----|----------|
| `200` | успех (для заказов — идемпотентный повтор существующего) |
| `201` | заказ создан впервые |
| `400` | ошибка валидации payload (неверный EAN, пустые поля, неизвестный EAN строки заказа) |
| `401` | нет/неверный токен |
| `404` | API выключен или организация по host не найдена |
| `409` | конфликт: EAN уже привязан к другому товару; изменённый payload существующего заказа; 0 или >1 активного склада |

Тело ошибки: `{ "error": "<текст>" }`. Тело успеха — см. ниже по endpoint'у.

## POST /api/integration/v1/items

Идемпотентный upsert номенклатуры. Товары создаются как **источник API**, партионный учёт (**LOT**),
единица **«шт»** (назначаются автоматически; выбор не требуется).

**Тело:** массив товаров — как `{ "items": [...] }` или голый массив.

```json
{
  "items": [
    { "externalId": "PROD-1", "name": "Сырок глазированный 40 г", "ean": "4607750000012", "sku": "SYR-40" }
  ]
}
```

Поле | Обяз. | Описание
-----|-------|---------
`externalId` | да | идентификатор товара во внешней системе; ключ идемпотентности `[организация, externalId]`
`name` | да | наименование
`ean` | да | заводской EAN-8/EAN-13; проверяется длина и контрольная цифра
`sku` | нет | внешний код (при коллизии уникальности `[организация, sku]` — `409`)

**Правила:**
- Повторная отправка того же `externalId` обновляет наименование/SKU и **не создаёт дубль**.
- EAN, уже привязанный к **другому** товару, **не перепривязывается** → `409`.
- Новый EAN для того же `externalId` **добавляется** тому же товару (у товара может быть несколько EAN).
- Товары, отсутствующие в очередной выгрузке, **не удаляются и не деактивируются**.
- Весь пакет **атомарен**: любая ошибка откатывает весь запрос (ничего не записывается).
- DELETE-endpoint отсутствует намеренно.

**Успех (`200`):**

```json
{ "ok": true, "processed": 1, "created": 1, "updated": 0 }
```

## POST /api/integration/v1/orders

Импорт внешнего заказа. Использует существующий импорт заказов; товар определяется **только по
активному EAN**. Склад — **единственный активный** склад организации.

**Тело:**

```json
{
  "externalId": "ORDER-1",
  "arrivalAt": "2026-08-10T09:00:00Z",
  "lines": [
    { "externalLineId": "LINE-1", "ean": "4607750000012", "quantity": 5 }
  ]
}
```

Поле | Обяз. | Описание
-----|-------|---------
`externalId` | да | идентификатор заказа; ключ идемпотентности `[организация, externalId]`
`arrivalAt` | нет | ISO-8601; ожидаемое время (ключ сортировки очереди)
`lines[].externalLineId` | да | идентификатор строки; уникален в пределах заказа
`lines[].ean` | да | активный EAN товара организации; неизвестный/неактивный → `400`
`lines[].quantity` | да | целое больше нуля

**Правила:**
- Точный повтор того же `externalId` с тем же содержимым — идемпотентен (`200`, `created:false`).
- Изменённый payload существующего `externalId` → `409` **без частичной записи**.
- Если активных складов `0` или `>1` → `409` с понятным описанием конфигурации.
- Импорт **не приписывается** реальному администратору (внутреннее `createdById = null`).
- Обратная отправка статусов пока не реализована.

**Успех:** `201` при первом импорте, `200` при идемпотентном повторе.

```json
{ "ok": true, "orderId": "clx...", "created": true }
```

## Примеры curl (токен условный — подставьте свой)

```bash
# Номенклатура
curl -sS -X POST https://rostagro.skladyx.ru/api/integration/v1/items \
  -H "Authorization: Bearer <INTEGRATION_API_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"items":[{"externalId":"PROD-1","name":"Сырок 40 г","ean":"4607750000012","sku":"SYR-40"}]}'

# Заказ
curl -sS -X POST https://rostagro.skladyx.ru/api/integration/v1/orders \
  -H "Authorization: Bearer <INTEGRATION_API_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"externalId":"ORDER-1","arrivalAt":"2026-08-10T09:00:00Z","lines":[{"externalLineId":"LINE-1","ean":"4607750000012","quantity":5}]}'
```

## Адаптер к 1С

Конкретный формат 1С в этом контракте **не фиксируется**. Планируемый адаптер — тонкий слой, который:
читает выгрузку 1С (товары/заказы), приводит поля к JSON выше (`externalId`, `name`, `ean`, `quantity`
и т.п.) и делает POST на эти endpoint'ы. Смена источника не потребует правок серверной логики склада.
