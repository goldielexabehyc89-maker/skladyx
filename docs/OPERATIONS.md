# SkladyX · Эксплуатационные правила

Как безопасно работать с живыми контурами SkladyX. Инвентарь по факту сервера —
[SERVER_INVENTORY.md](SERVER_INVENTORY.md). Деплой — [DEPLOY.md](DEPLOY.md).
Восстановление — [RESTORE.md](RESTORE.md).

---

## 1. Главное правило: repo ≠ production facts

**Репозиторий — не источник истины о продакшене.** Он говорит, что *должно* быть,
а не что *есть*. Источник истины — сам сервер.

На сервере **нет `.git`** (код доставляется rsync'ом), поэтому «посмотреть версию прода
git'ом» невозможно. Файлы на сервере могут отличаться от `main`, и это нормальное
состояние между выкатками.

**Живой пример (сверка 2026-07-23, HEAD `9cdeacb`):**

| Контур | Состояние |
|---|---|
| staging `/opt/skladyx-staging` | 184/184 файла совпадают с HEAD |
| prod `/opt/skladyx` | 5 файлов отсутствуют, 4 отличаются |

При этом **код приложения** (`src/`, `prisma/`, `package.json`, `Dockerfile`) на prod
совпадал с HEAD — расходились только документация и ops-тулинг. Вывод: «prod отличается
от main» ≠ «на проде другой код». Нужно смотреть, *какие именно* файлы разошлись.

### Как сверить фактическое состояние (read-only)

**[локально на Mac]**, из корня репозитория:

```bash
TARGET=/opt/skladyx          # или /opt/skladyx-staging
git ls-files | xargs md5 -r | awk '{print $1" "$2}' | sort -k2 > /tmp/local.txt
git ls-files | ssh -i ~/.ssh/sklad_prod_ed25519 root@104.171.136.35 \
  "cd $TARGET && while IFS= read -r f; do [ -f \"\$f\" ] && md5sum \"\$f\"; done" \
  | awk '{print $1" "$2}' | sort -k2 > /tmp/srv.txt

# отсутствуют на сервере:
comm -23 <(cut -d' ' -f2 /tmp/local.txt) <(cut -d' ' -f2 /tmp/srv.txt)
# отличаются по содержимому:
join -j2 /tmp/local.txt /tmp/srv.txt | awk '$2!=$3{print $1}'
```

Пустой вывод обеих команд = контур идентичен текущему HEAD.

**Правило:** прежде чем утверждать что-либо про прод («там стоит версия X», «бэкапы
настроены», «порт закрыт») — **проверь на сервере**. Не переписывай вывод из репозитория
или из прошлого отчёта.

## 2. Чеклист проверки контура (prod / staging)

Выполнять **[на сервере]**, подставив нужный контур:

| Что | prod | staging |
|---|---|---|
| путь | `/opt/skladyx` | `/opt/skladyx-staging` |
| compose file | `docker-compose.yml` | `docker-compose.staging.yml` |
| app port | `127.0.0.1:3003` | `127.0.0.1:3013` |
| домен | `rostagro.skladyx.ru` | `staging-rostagro.skladyx.ru` |

```bash
cd /opt/skladyx                                  # или /opt/skladyx-staging
docker compose ps                                # app Up, db Up (healthy)
docker compose config --quiet                    # валидация БЕЗ вывода секретов
ss -tulpn | grep -E ':3003|:3013|:5432'          # см. раздел 3
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3003/login       # 200
curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' http://127.0.0.1:3003/warehouse  # 307 -> /login
ls -lht /opt/backups/postgres | head -3          # свежесть бэкапа
tail -20 /opt/backups/backup.log                 # последний прогон
nginx -t                                         # конфиг валиден
certbot certificates                             # сроки сертификатов
```

Снаружи (**[локально на Mac]**): `/login` → `200`, `/warehouse` → `307` → `/login`,
`/app` → `307` → `/warehouse`.

> ⚠️ Всегда `docker compose config --quiet`. Без `--quiet` команда печатает `DATABASE_URL`
> с паролем БД в открытом виде (см. раздел 5).

## 3. Как проверять порты (с контрольными примерами)

```bash
ss -tulpn
```

**Ожидаемая картина (норма):**

| Строка | Оценка |
|---|---|
| `127.0.0.1:3003` (docker-proxy) | ✅ prod app — только loopback |
| `127.0.0.1:3013` (docker-proxy) | ✅ staging app — только loopback |
| `0.0.0.0:80`, `0.0.0.0:443` (nginx) | ✅ публичный вход, так и задумано |
| `0.0.0.0:22` (sshd) | ✅ инфраструктура |
| `127.0.0.53:53`, `127.0.0.54:53` (systemd-resolve) | ✅ ОС |
| `127.0.0.1:39471` (containerd) | ✅ docker, только loopback |
| `0.0.0.0:10050` (zabbix_agentd) | ⚠️ **не SkladyX** — агент мониторинга хостера |

**Признаки инцидента:**

| Строка | Что значит |
|---|---|
| `0.0.0.0:5432` или `:::5432` | 🔴 **БД опубликована наружу** — так быть не должно ни на одном контуре |
| `0.0.0.0:3003` / `0.0.0.0:3013` | 🔴 app минует nginx и доступен напрямую из интернета |
| новый неизвестный `0.0.0.0:*` | 🟡 разобраться, чей процесс, прежде чем что-то делать |

Контрольная проверка «БД закрыта» (ожидаем пустой вывод):

```bash
ss -tulpn | grep ':5432'
```

Порт `5432` виден **только внутри** compose-сети (`docker ps` покажет `5432/tcp` без
`0.0.0.0:` слева) — это норма.

## 4. Не приписывай SkladyX чужое

На сервере живут процессы, кроны и таймеры, к SkladyX **не относящиеся**. Прежде чем
трогать/чинить/описывать что-то как «наше» — определи владельца.

**Как определять принадлежность (а не угадывать):**

| Сущность | Признак «наше» |
|---|---|
| контейнер | имя начинается на `skladyx-` / `skladyx-staging-`; `docker inspect` → `com.docker.compose.project` = `skladyx` или `skladyx-staging` |
| volume | имя `skladyx_skladyx_*` (prod) или `skladyx_staging_*` (staging) |
| порт | процесс `docker-proxy` и порт `127.0.0.1:3003/3013` |
| nginx-сайт | файл в `sites-enabled/` с `server_name *.skladyx.ru` |
| cron | файл `/etc/cron.d/skladyx-*` |
| путь | `/opt/skladyx`, `/opt/skladyx-staging`, `/opt/backups` |

**Заведомо НЕ наше** (проверено 2026-07-23): `zabbix_agentd:10050` · `sshd` ·
`systemd-resolve` · `containerd` · `certbot.timer` и `/etc/cron.d/certbot` ·
`/etc/cron.d/{sysstat,e2scrub_all}` · таймеры `apt-daily*`, `logrotate`, `man-db`,
`motd-news`, `dpkg-db-backup`, `update-notifier*`, `systemd-tmpfiles-clean` ·
каталог `/opt/sklad` (пустой, происхождение неизвестно, нашим деплоем не используется).

Актуальный разбор «наше / не наше» — в [SERVER_INVENTORY.md](SERVER_INVENTORY.md).

> Правило: **не удаляй и не «чини» то, чей владелец не установлен.** Сначала выясни,
> потом действуй. Отсутствие процесса в нашем инвентаре ≠ «он лишний».

## 5. Запрет секретов в URL

- ❌ Никаких токенов/паролей/ключей в query-строке: `https://host/api?token=...`.
  URL попадают в логи nginx, историю shell, `docker logs`, реферер — это утечка.
- ✅ Секреты передаются заголовком (`Authorization`) или телом запроса.
- ❌ Не вставляй секреты в примеры команд в документации и в отчёты.
- ⚠️ `docker compose config` печатает `DATABASE_URL` с паролем — использовать
  **только `--quiet`**. Аналогично не выводить `.env` целиком: маскируй значения
  (`sed -E 's/(PASSWORD|SECRET|PRIVATE)=.+/\1=***/'`).
- Секреты живут **только** в `/opt/<контур>/.env` (права `600`, владелец `root`)
  и никогда — в git.

## 6. Expand / contract при смене auth, секретов, webhooks

Никогда не меняй общий секрет «одним махом» — это гарантированный простой. Схема из трёх фаз:

1. **Expand** — добавить новое, **не удаляя старое**. Приложение принимает и старый,
   и новый секрет/ключ/URL одновременно.
2. **Migrate** — перевести всех потребителей на новое (клиенты, вебхуки, интеграции,
   PWA-подписки). Убедиться по логам/метрикам, что старое больше не используется.
3. **Contract** — только теперь удалить старое.

Частные случаи для SkladyX:

- **`AUTH_SECRET`** — подписывает сессионные JWT (cookie `skx_session`). Смена
  **инвалидирует все активные сессии**: пользователи разлогинятся. Менять в тихое окно
  и предупреждать владельца.
- **VAPID-ключи** — привязаны к существующим push-подписками. Смена ключей **ломает все
  подписки**; потребуется переподписка устройств. Пара ключей у prod и staging **разная** —
  не переносить между контурами.
- **`DB_PASSWORD`** — менять согласованно: пароль в `.env` и в самой БД должны совпасть,
  иначе app не поднимется. Перед сменой — свежий бэкап.
- **Вебхуки/внешние URL** — сначала поднять новый endpoint, перевести отправителя,
  и лишь затем гасить старый.

## 7. Статусы бэкапов

Не говори «бэкапы есть» — уточняй **уровень**. Пять независимых статусов:

| Уровень | Что означает | Статус SkladyX (2026-07-23) |
|---|---|---|
| **script exists** | скрипт бэкапа написан и лежит в репозитории | ✅ `scripts/prod/backup-{postgres,uploads,all}.sh` |
| **scheduled** | запускается автоматически по расписанию | ✅ `/etc/cron.d/skladyx-backup`, ежедневно 03:20 UTC |
| **fresh backup verified** | свежий файл реально создан, ненулевой, лог без ошибок | ✅ дамп 2026-07-23 03:20, 80K, лог `DONE OK` |
| **offsite copy verified** | копия лежит **вне этого сервера** | ❌ **НЕТ** — только локально в `/opt/backups` |
| **restore verified** | из дампа реально восстановились и проверили данные | ✅ однократно 2026-07-15 (temp-контейнер: 35 таблиц, `Company`, 14 миграций) |

**Следствия:**
- Потеря сервера/диска = потеря бэкапов. Offsite — незакрытый риск.
- `restore verified` подтверждён на дампе от 2026-07-15, не на каждом свежем.
  Периодическая проверка восстановления — по [RESTORE.md](RESTORE.md), раздел 6
  (temp-контейнер, prod не трогается).
- Бэкапы лежат в `/opt/backups`, **вне** каталогов деплоя, поэтому `rsync --delete`
  их не удаляет. Никогда не переноси их внутрь `/opt/skladyx*`.

## 8. Prisma migrations — forward-only

`prisma migrate deploy` применяет миграции **только вперёд**. Отката миграций нет.

> **Откат кода НЕ откатывает схему БД.**

Если релиз содержал миграцию и его откатили:

- старый код может встретить **новую** схему → ошибки рантайма;
- вернуть схему можно **только restore'ом из бэкапа** по [RESTORE.md](RESTORE.md),
  с отдельным подтверждением владельца (restore перезаписывает данные).

Поэтому:

1. Любой релиз с миграцией сначала проходит **staging** (см. [DEPLOY.md](DEPLOY.md)).
2. Перед prod-выкаткой — свежий бэкап (`deploy-prod.sh` снимает его сам и
   останавливается, если бэкап упал).
3. Миграции проектировать в стиле expand/contract (раздел 6): сначала аддитивно
   (новая колонка nullable/с дефолтом), удаление старого — отдельным поздним релизом.
   Так откат кода остаётся безопасным без restore.
